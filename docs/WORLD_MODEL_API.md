# World-Model Plugin API (Draft)

**Purpose:** let a lab submit a learned predictive model without forking RoyaleBench, and let the same model be evaluated both as a forecaster and as part of a model-based playing agent.

A world model is not automatically a policy. RoyaleBench therefore separates:
1. predictor submission;
2. common-planner submission using that predictor;
3. arbitrary custom agent submission.

## 1. Two prediction problems

### 1.1 Conditional dynamics

Question: given the current observable context and the actions of both players, what state follows?

Input:
- current FAIR observation/history;
- a sequence of own actions;
- a sequence of opponent actions;
- requested horizons and number of samples.

This is a teacher-forced dynamics evaluation. It measures the transition model, not the model's ability to predict what an opponent will choose.

### 1.2 Opponent response

Question: given public history and the opponent's information, what might the opponent do next?

Input:
- current FAIR observation/history;
- only the acting seat's public information;
- no future opponent actions.

Output:
- a distribution over opponent actions or action sequences;
- uncertainty/calibration fields.

This is a separate prediction task. A model supplied the true future opponent actions is not being evaluated as an opponent predictor.

### 1.3 Model-based playing

The planner proposes candidate own-action sequences. For each candidate, the benchmark planner samples opponent-response hypotheses from a fixed opponent population or from a registered opponent model, then asks the world model to predict the resulting futures. The planner scores the predicted outcomes and executes only the first action.

A participant may supply a custom planner in the general agent leaderboard. The controlled model-based leaderboard uses the benchmark's common planner so that differences are primarily attributable to the predictive model.

## 2. Required predictor interface

A model adapter implements these logical operations:

- reset(match_manifest, seat, model_config): clear all per-match state.
- predict(request) -> prediction_batch: predict one or more future states at requested horizons.
- close(): flush diagnostics and release resources.

Implementations may run as:
- a local Python class;
- a subprocess or container;
- an HTTP/WebSocket service.

The control schema is JSON. Large visual tensors or predicted frame sequences should use a declared binary transport (for example, a content-addressed file/object or a documented tensor payload), not huge base64 JSON fields.

## 3. Prediction request

Every request contains:
- schema: world-model-request.v1;
- request_id, match_id, decision_id, observation_hash;
- observation_modality: structured_fair or visual;
- context: current FAIR state or frame window plus allowed history;
- conditioning_mode;
- action_sequences: candidate actions indexed by relative engine tick;
- horizons_ticks: the future ticks to predict;
- num_samples;
- opponent_hypothesis_id when the benchmark planner supplies one;
- requested output representation and schema version.

Supported conditioning modes:

**joint_actions_teacher_forced**  
Both seats' actions are supplied for the prediction interval. Used only for conditional dynamics evaluation.

**own_actions_plus_opponent_hypothesis**  
Own candidate actions are supplied; opponent actions are generated by a named policy/hypothesis. Used in the controlled model-based planner.

**opponent_action_prediction**  
No future actions are supplied. The model predicts the opponent's action distribution from public history.

The request must never include hidden opponent hand/elixir, future action logs, internal RNG state or privileged simulator state in a FAIR benchmark track.

## 4. Canonical prediction output

The comparable structured forecast output is a batch of samples. Each sample contains predictions at one or more requested horizons:

- horizon tick;
- probability/weight for the sample;
- predicted visible entities and their identities/types;
- positions in the acting seat's frame;
- HP/health estimates where observable;
- predicted towers/crowns/resources;
- projectile and spell/effect objects;
- spawn/death/attack/damage/ability events;
- optional uncertainty fields.

The output schema must pin units, coordinate frame, entity identity semantics, missing-value semantics and probability interpretation. A model cannot return an unlabelled list of numbers and claim a comparable forecast score.

For variable-size entity sets, predicted entities should include a stable identity when tracking an existing entity and a new identity for predicted spawns. Existence probability and class probability may be returned when the model is uncertain.

The benchmark scores only the permitted target fields. Privileged simulator state is used as ground truth inside the evaluator, not included in the model input. A model may internally represent hidden state, but hidden-state prediction is not part of the FAIR score unless a separate oracle track is explicitly declared.

## 5. Output families and separate tracks

### Structured state predictor

Returns canonical state/event predictions. Eligible for common multi-step prediction metrics and the common-planner track.

### Visual future predictor

Returns rendered future frames conditioned on actions. Eligible for visual forecasting metrics. It enters the model-based playing track only if a documented controller can convert its outputs into action values using an agreed evaluation method.

### Latent-only predictor

Returns latent states without a decoder into the canonical state or frame protocol. Eligible for a representation/latent-consistency study with a model-specific metric, not directly comparable to decoded state forecasters and not automatically eligible for the common planner.

### Hybrid predictor

May return latent predictions plus decoded entities/events. The decoded output is scored under the common forecast schema; latent outputs are supplementary.

## 6. Common planner contract

The controlled planner has fixed, versioned:
- candidate action generator;
- candidate sequence length/horizon;
- opponent policy population and sampling distribution;
- number of model queries/samples;
- value/utility function;
- replanning cadence;
- compute/query budget.

At each decision:
1. receive current FAIR observation;
2. generate the same legal/tap-point candidate set for every model;
3. generate opponent hypotheses from the fixed distribution;
4. query the registered model for candidate futures;
5. score each candidate using the common evaluator;
6. select one action;
7. execute only that action through the canonical engine;
8. observe the real result and replan.

The planner does not receive the true future opponent action. A privileged oracle planner using the engine's internal state is a separately labelled upper-bound diagnostic, never a normal leaderboard entrant.

## 7. Fair comparisons

For prediction comparisons, pin:
- training/validation/test match-level splits;
- engine/data version;
- input observation modality;
- action-conditioning mode;
- horizons and sampling count;
- canonical output version;
- model version and weights/checkpoint digest.

For model-based agent comparisons, also pin:
- planner version;
- candidate set and opponent hypotheses;
- number of samples/model queries;
- planning time or compute budget;
- agent action-resolution and latency mode.

Report:
- multi-horizon state/event metrics;
- uncertainty calibration;
- counterfactual ranking accuracy;
- predictor latency and compute;
- match outcomes when connected to a controller.

Prediction accuracy never contributes directly to the competitive rating. A world model can be an excellent forecaster and a poor player; the two results must remain visible separately.

## 8. Failure and compatibility

A predictor that cannot condition on actions is not eligible for the action-conditioned dynamics track. A predictor that produces only frames is not silently decoded by a hidden benchmark model and then treated as a structured predictor. Any perception/decoder used to interpret predictions must be declared and held constant for comparisons.

Requests and responses echo request_id, decision_id and observation_hash. Responses for stale requests are rejected. A timeout, malformed output or incompatible schema is recorded as a technical model failure, never silently replaced with the true engine state.
